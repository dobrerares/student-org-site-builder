# Cloudflare Pages — deployment reference

## Why Cloudflare Pages

The PRD (Distribution & ownership) commits to **Cloudflare Pages as the
sole recommended/documented host** for v1. Reasons:

- Free tier supports static sites of the size a student-organization
  produces (the build pipeline budgets each page to ~50 KB HTML, ~15 KB
  CSS, ~10 KB JS — easily inside any free quota).
- Two ingestion paths fit the user spectrum: drag-and-drop the `dist/`
  folder for non-technical officers, Git-connected for officers
  comfortable with GitHub.
- Free TLS certificates on custom domains, no DIY ACME work.
- No vendor-locked features in our build output: the `dist/` folder is a
  plain static site; if Cloudflare ever degrades, the same folder
  deploys to Netlify, GitHub Pages, or any S3-compatible bucket without
  changes.

Other hosts will technically serve the same `dist/`, but the PRD
explicitly excludes them from the documented path:

> **Out of scope:** No FTP/SFTP, Netlify, GitHub Pages, or Vercel
> integration in v1 docs. Cloudflare Pages only is documented and
> recommended.

If your organization needs SFTP or Netlify for compliance reasons, the
output is still portable — the `dist/` folder is self-contained — but
the support contract is "best effort, not documented."

## What ships in every export

Every export zip contains:

- `data.json` — the canonical site data (source of truth).
- `assets/` — content-addressed media (hash-named files).
- `dist/` — the built static site (HTML + CSS + ≤10 KB JS).
- `DEPLOY.md` — user-facing deployment guide, language-matched to the
  editor's UI language at export time.

The user-facing `DEPLOY.md` is generated by `@sosb/zip`'s
`generateDeployMd()` function (see `packages/zip/src/deploy-md.ts`).
The same function is called by the in-app "Open guide" modal, so the
content shown on screen is byte-identical to the file in the zip.

## The two deploy paths

The user-facing `DEPLOY.md` documents both paths in detail. This
section is the **maintainer's** quick reference; defer to the in-zip
copy for the user-friendly walkthrough.

### Path 1 — Direct upload via the dashboard

1. **Create application** → **Pages** tab → **Upload assets**.
2. Project name → defaults to `<name>.pages.dev`.
3. Drag-and-drop the `dist/` folder.
4. **Deploy site** → live within seconds.
5. Updates: re-upload `dist/` to the same project.

**When to recommend this path.** Non-technical officers. No GitHub
account. One-off updates rather than continuous changes.

### Path 2 — Git-connected

1. Push `dist/` (or the whole zip with `dist/` as the build-output
   folder) to a GitHub repository.
2. **Create application** → **Pages** tab → **Connect to Git** →
   authorize and select the repo.
3. Build command: empty. Build output directory: `/` (if pushing only
   `dist/`) or `dist` (if pushing the whole zip).
4. **Save and Deploy** → auto-deploys on every push to the main branch.

**When to recommend this path.** Officers who already have a GitHub
account, or organizations that want preview deploys for non-main
branches.

## Custom domain configuration

The `*.pages.dev` subdomain works immediately. For a branded domain:

1. **Custom domains** tab in the Pages project → **Set up a custom
   domain** → enter the apex domain (e.g. `historipol.ro`).
2. Cloudflare displays a CNAME target (`<project>.pages.dev`).
3. Add the CNAME at the registrar's DNS panel (or, if the domain is
   already on Cloudflare's nameservers, the record is added
   automatically).
4. Wait for DNS propagation (minutes to hours).
5. Once the domain shows as **Active**, Cloudflare provisions a free
   TLS certificate automatically. HTTPS becomes available within a few
   minutes after activation.

**Apex vs. subdomain.** Most registrars support CNAME on subdomains
(`www.example.org`) but not on apex domains. If the site is at the
apex, either (a) move DNS to Cloudflare's nameservers, which supports
"CNAME flattening" at the apex, or (b) use a CNAME on `www` plus a
redirect from the apex.

## Re-deploying with a new `siteUrl`

The build pipeline (`@sosb/build`) takes `siteUrl` as a build-time
option (see ADR 0004). The same `data.json` produces different
`dist/index.html` outputs depending on `siteUrl`:

- `siteUrl = undefined` — relative URLs, no canonical/og:url/og:image,
  relative `<loc>` in sitemap.
- `siteUrl = "https://historipol.ro"` — absolute canonical/og:url tags,
  absolute `Sitemap:` directive in robots.txt, absolute sitemap entry.

When a user moves from `*.pages.dev` to a custom domain, **they must
re-export from the editor with the new `siteUrl`** for the canonical
URLs and sitemap to be correct. The `DEPLOY.md` file in the export
flags this requirement when the build context already has a `siteUrl`
set.

## Verification protocol (maintainer-only)

When you ship a release:

1. Export a zip from a clean editor session against the demo template.
2. Sign in to a Cloudflare account.
3. Walk Path 1 (direct upload) end-to-end.
4. Walk Path 2 (Git-connected) end-to-end.
5. Connect a test custom domain (any registrar) and verify HTTPS
   activates.
6. Capture screenshots at the steps marked in the in-zip `DEPLOY.md`
   and commit them to `docs/deploy/screenshots/` (see naming convention
   in `docs/deploy/screenshots/README.md`).

If the Cloudflare dashboard UI has drifted from what the generated
`DEPLOY.md` describes, update the strings in
`packages/zip/src/deploy-md.ts` and re-run `pnpm test` to refresh the
golden snapshots.

## When Cloudflare changes things

Cloudflare ships dashboard updates frequently. Failure modes we have
seen on similar products and what to do:

- **Menu item renamed.** Update the corresponding string in
  `packages/zip/src/deploy-md.ts` (both RO and EN bundles), refresh
  golden snapshots with `pnpm test`, commit.
- **A step disappears or re-orders.** Update the numbered list in the
  same file. The test for "section order" only enforces section
  identity, not step text — prose changes within a section are free.
- **Dashboard URL changes.** The doc references
  `https://dash.cloudflare.com/`; if Cloudflare retires that origin,
  update it in both bundles and refresh snapshots.
- **Free-tier limits change.** The doc says "at the time of writing"
  — do not promise behaviour we have not verified. If the limit moves
  in a way that affects student-org-sized sites, update the
  prerequisite item and re-run snapshots.

We deliberately do not promise specific Cloudflare features we do not
control (uptime SLA, edge-cache hit rate, free-tier permanence). The
test suite enforces this — adding "guaranteed" or "free forever" to
the bundles fails CI.

## Out of scope

- **Cloudflare Workers / Pages Functions.** v1 ships static sites only.
  No edge functions, no API routes.
- **Other static hosts.** Per PRD, Cloudflare Pages is the sole
  documented target.
- **Custom email forwarding via Cloudflare Email Routing.** The site
  does not run mail; the contact block uses `mailto:` only.
- **Cloudflare Analytics / Web Analytics.** Telemetry is out per PRD
  ("Telemetry: none").
