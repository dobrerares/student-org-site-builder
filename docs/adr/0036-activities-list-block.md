# 0036 — activitiesList block

- **Status:** Accepted
- **Date:** 2026-05-05
- **Issue:** #11

## Context

Issue #11 ships the `activitiesList` block — one of the six mandatory
blocks listed in the PRD's block library. It carries a heading, an
optional intro, and a list of items, each with a title, optional
description, optional image, optional link with optional label, and an
optional badge string (e.g. `Anual` / `Lunar` / `Sezonier`).

Three layouts are required by the AC: `cards`, `list`, `alternating`. No
4th layout, no custom layouts, no runtime layout switching (out-of-scope
per the issue triage). Image fields use `AssetRef` from `@sosb/assets`
(#8); the upload entrypoint enforces alt text. The editor form is
auto-generated by the same `fieldsFromSchema` helper that drives the
site-spine form (#7).

The PRD does **not** pin:

- Whether the three layouts share a single component or fork into three.
- The exact shape of the asset reference at the schema layer (vs the
  runtime AssetRef from `@sosb/assets`).
- Whether alt text on item images is an `error` or a `warning` at the
  schema layer.
- Where the three layouts' difference lives (markup vs CSS).

This ADR records those choices.

## Decision

### One component, three layouts via `data-layout`

`ActivitiesList` is a single Preact component. The three layouts share
one DOM tree and differ only via a `data-layout="cards|list|alternating"`
attribute on the root `<section>`. Theme CSS targets each layout via the
attribute selector — `[data-block="activitiesList"][data-layout="cards"]`
etc.

This keeps the structural / accessibility concerns in one place and
defers visual differences to CSS, which is the right seam: themes
(#28-#31, #47) own the visual treatment of each layout, and the renderer
owns the semantic structure that does not change.

Forking into three components would have required either a
`type: "activitiesList:cards"` schema split (heavy) or a runtime
component dispatch on `layout` with three nearly-identical templates
(low value).

### `AssetRef`-shaped image field, declared inline at the schema layer

`@sosb/schema` deliberately does not import `@sosb/assets`: the schema
package is zero-runtime-dep (Zod only) and assets is browser-coupled.
We re-declare the `AssetRef` shape inline as `ActivityImageRefSchema`
with the same field names, so:

- The `AssetRef` returned from `uploadAsset` plugs straight into the
  schema with no transformation (the integration test in
  `packages/assets/test/activities-list-integration.test.ts` proves
  this).
- The schema package stays decoupled from browser-only code paths.
- Future edits to `AssetRef` need a coordinated schema change. We
  accept that cost — `AssetRef` is a stable API per ADR-0004 and
  v1's expansion path is multi-output (#37), which extends the
  surface rather than reshaping it.

### Alt text is an `error` at the schema layer

`ActivityImageRefSchema.alt` is `z.string().min(1)`. An empty alt fails
schema parse, which surfaces as an `error` from `validateBlock` and
hard-blocks the editor's "publish" path (per the PRD severity model,
`error` = blocking-on-confirmation).

This is a stricter rule than the hero block's "missing alt → warning"
nudge. Two reasons:

1. The activitiesList ships images more directly: the image is the
   visual anchor of each item, so a missing alt has a worse a11y impact
   than a hero background.
2. The `AssetRef` already carries `alt` from the upload-time
   enforcement in `@sosb/assets` (#8); a freshly-uploaded asset can
   never have empty alt. The schema rule catches the case where an
   imported / migrated site had an empty alt slip through.

Both checks coexist by design (mirroring ADR-0004's rationale): the
upload path enforces at write time; the schema enforces at the data
layer for any path that wasn't an upload (imports, migrations, manual
JSON edits).

### Implicit-CTA pattern when an item has a link without a label

When an item has a `link.href` but no `link.label`, the renderer emits
an anchor with `aria-label={item.title}` and a visually-aside chevron
(`→`). The accessible name is derived from the item title; the visible
glyph is decorative (`aria-hidden="true"`).

This satisfies the AC's "per-item link with optional label renders as
accessible CTA" without forcing the schema to require a label or
forcing the renderer to invent visible text. Themes can target
`[data-cta="implicit"]` to style the chevron.

### Three goldens, one per layout × Academic-stub

Per the AC, golden-file tests cover each layout × Academic theme. The
Academic theme itself is issue #47; until it lands, `themeId="academic"`
falls back to the stub theme (existing renderer behaviour). The three
goldens are committed against the stub fallback today and will
regenerate against the real Academic theme when #47 substitutes the CSS.

## Consequences

- The block's structural HTML is fixed by the renderer; visual
  treatment per layout is owned by themes, which is the right
  separation for the PRD's "themes wholesale-replace presentation"
  model.
- Adding a 4th layout is one schema-enum entry, one renderer literal
  branch (none today, since layout is purely a `data-layout` attribute
  no further branching), and per-theme CSS. We do **not** ship a 4th
  layout in v1 (out of scope per #11 triage).
- The schema package now has an inline `AssetRef` shape declaration.
  Future asset-pipeline shape changes (extending fields beyond v1, e.g.
  `srcset` for #37) need coordinated updates here too.
- The editor's auto-form (#7's `fieldsFromSchema`) already produces a
  field tree for the activitiesList data without any code change. Block
  forms (#9-#22) are still each-block-individual issues; this issue
  doesn't ship a UI for the activitiesList — it ships the schema, the
  renderer, and the integration boundary the future block-form work
  consumes.

## Alternatives considered

- **Three separate components, one per layout.** Rejected: forks the
  semantic / a11y structure across three near-identical templates and
  pushes layout coupling into the renderer instead of the theme.
- **Image as a string path (no AssetRef).** Rejected: loses width /
  height / alt at the data layer, breaks the dedup contract from #8,
  and forces every consumer to round-trip through the metadata sidecar.
- **Alt as a warning (matching hero).** Rejected: alt on item images is
  more visible to users than a hero background, and the upload-time
  rule already produces non-empty alt for any newly-uploaded asset.
  An `error`-tier rule prevents stale data from publishing silently.
- **Render layout differences in markup.** Rejected: the structural
  shape doesn't change between layouts, only the visual flow. Themes
  own visual flow; the renderer owns semantics.

## Out of scope

- A 4th layout, custom layouts, or layout switching at runtime.
- Filtering, sorting, or pagination of items (small curated list in
  v1 per PRD).
- Editor form UI (block forms are each-block-individual; the
  auto-form already handles the activitiesList data tree without
  bespoke code).
- Theme styling beyond the stub fallback (Academic theme is #47;
  other themes are #28-#31).
- Asset pipeline changes — consumed from #8 unmodified.
